# Dataset editor

The trusted-maintainer editor lives in `apps/editor` and edits this repository's `data/` files. It
uses the local `@pokepc/dataset` workspace package for schemas, types and filesystem access.
Existing Pokemon and game images load from `https://static.pokepc.net`.

## Development

Run from the repository root:

```sh
pnpm install
pnpm dev:editor
pnpm dev:openapi
pnpm dev
```

`dev:editor` builds the local dataset helpers and starts the editor on `http://127.0.0.1:3003`.
`dev:openapi` starts the OpenAPI preview on `http://localhost:4173`. `dev` runs both in parallel;
Ctrl+C stops both. Restart `dev:editor` after changing dataset helper source code to rebuild it.
JSON edits are read directly and do not require a library rebuild. Do not run a second editor
against the same files while a save is in progress.

No `.env` file is required. The filesystem helper locates the owning dataset package and selects its
`data/`, independent of the working directory or whether helpers run from source or build output. An
optional `POKEPC_DATASET_DIR` overrides this for disposable QA copies. Prefer absolute paths;
explicit relative overrides resolve against the process working directory. Invalid overrides fail
instead of falling back to the maintained data. Editor dev/start commands disable memory caching so
save and reload see current files.

The app remains local maintainer tooling without authentication. Keep it on loopback; shared hosting
requires a separate access-control design. `data-next/` is generated by its existing pipeline and is
outside the editor's scope.

## Build, formatting and verification

```sh
pnpm build:lib
pnpm build:editor
pnpm typecheck:editor
pnpm test:editor
pnpm --filter @pokepc/editor exec playwright install chromium
pnpm test:e2e:editor
pnpm --filter @pokepc/editor format
pnpm format
```

Editor commands prepare the local compiled dataset exports automatically. `build:lib` compiles
helpers without regenerating `data-next/` or formatting source data. The root `build` generates and
packages the dataset. The editor workspace and its assets are excluded from the npm package. Root
`format` formats the repository, including data; the filtered editor command formats only the app.

The browser suite starts development and production servers on ports 3103 and 3104, each using its
own copy of `data/` under `.local/editor-e2e`. It verifies Pokédex save/reload and classic/modern
preset create/save/delete, checks persisted values and unchanged siblings, and opens availability
and maintenance routes. Fixture images from the CDN are stubbed with gray squares and the remote
font stylesheet is stubbed, while app URL generation remains unchanged. Screenshots and traces are
written under `apps/editor/test-results`; `apps/editor/playwright-report` contains the HTML report.
The root Vitest suite covers dataset integrity and filesystem roots; the editor Vitest suite covers
its validation and business rules separately.

## Maintenance scripts

The Champions storage repair is at `src/scripts/fix-champions-storables.ts`; use
`DRY_RUN=1 bun src/scripts/fix-champions-storables.ts` from the root to preview it. The female-form
generation repair is at `apps/editor/app/scripts/fix-pokemon-data.ts` and uses the same local
filesystem helpers. Review these intentionally mutating scripts and the target before running them.

## Pokemon Availability Editing

Pokemon availability edits must sanitize selected game ids, preserve dataset ordering, require a
valid debut game, and validate the saved availability fields against the Pokemon schema subset
before writing the Pokemon JSON file.

### Does Not Apply To

- Non-availability Pokemon fields.
- Dataset migration scripts that intentionally operate outside the Pokemon editor workflow.

### Examples

- Unknown game ids are removed from availability arrays.
- Empty `shinyLockedIn` saves as omitted/undefined in the JSON file.
- If the draft has no valid debut game, the current Pokemon debut is used as fallback when possible.

### Edge Cases

- Debut candidates may include game sets as well as games, following the current logic for
  `gamesets`.
- Pokemon shown in the editor are currently filtered to dex numbers from `1` through `1386`.

## Game Availability Editing

Game-perspective availability edits must compare draft and baseline availability, update only
impacted Pokemon records, normalize all affected game membership arrays to valid ordered ids, and
validate availability fields before writing.

### Does Not Apply To

- Game metadata editing.
- Direct Pokemon-perspective availability saves, which follow the Pokemon availability rule.

### Examples

- Adding a Pokemon to a game's obtainable section adds that game id to the Pokemon's `obtainableIn`.
- Removing the selected game as a Pokemon debut derives a fallback debut from remaining availability
  candidates.
- Saving a draft with no diffs returns success without writing Pokemon files.

### Edge Cases

- Selected games with `gen > 0` cap helper lists to Pokemon whose generation is less than or equal
  to the game generation.
- Battle-only Pokemon are included in transfer-only helper calculations where applicable.
- Female-form helper behavior is derived from Pokemon form relationships.

## Pokedex Editing

Pokedex edits must keep the Pokedex id read-only, validate general fields and entries before saving,
normalize optional text fields, and parse the final payload through the Pokedex schema before
writing the JSON file.

### Does Not Apply To

- Creating new Pokedex files.
- Pokemon availability or game availability saves.

### Examples

- Pokedex name is required and must be 50 characters or fewer.
- Generation must be an integer between `0` and the dataset latest generation.
- Entry Pokemon ids must exist in the dataset.
- Entry dex numbers must be integers from `0` through `99999`.

### Edge Cases

- `shortDesc` becomes omitted when blank.
- `desc`, `region`, `baseDex`, and `pkApiId` become `null` when blank.
- Batch-add helpers can insert entries at the bottom or below an anchor row.

## Bulk Field Maintenance

Bulk field maintenance operations must validate the target, operation, field path, default JSON
payload, rename path, move pivot, and dry-run flag before applying mutations to dataset files.

### Does Not Apply To

- Arbitrary JSON files outside the supported maintenance targets.
- Dataset transformations performed by separate scripts.

### Examples

- Add operations require a valid JSON default value.
- Rename operations require a valid destination dot path different from the source.
- Move operations require a sibling pivot key and `before` or `after` position.
- Dry-run mode reports the number of changed records without writing files.

### Edge Cases

- Aggregate targets must be JSON arrays.
- Pokemon and game targets operate over ids loaded from the dataset package.
- Object path parsing allows dot notation with letters, numbers, `_`, and `-`.

## Box Preset Editing

Box preset edits must preserve the selected variant, game set, preset id, sibling preset/index
membership, and game-driven box sizing while validating the selected preset against the matching
classic or modern dataset box preset schema before writing.

### Does Not Apply To

- Creating or inferring modern preset files from classic files.
- Autosave, multi-user locking, audit trails, or authentication.

### Examples

- Dragging an occupied cell onto another occupied cell swaps the two cell values.
- Dragging an occupied cell onto an empty stored cell moves the value and clears the source.
- Dragging an occupied cell to the trash target clears the source cell.
- Dragging a drawer Pokemon into an empty stored cell inserts that Pokemon and leaves the drawer
  item available.
- Dragging a drawer Pokemon onto an occupied cell is rejected to avoid accidental replacement.
- Compacting a box moves occupied slots to the beginning in their current order and leaves the same
  number of stored empty slots at the end.
- Cell context-menu move actions remove the selected occupied slot and reinsert it at the requested
  position, shifting intervening occupied or empty slots instead of swapping with a target slot.
- Cell context-menu remove clears the selected occupied slot without rearranging the remaining box
  slots.
- Cell context-menu empty-slot insertion places an empty stored slot immediately after the selected
  occupied slot when the box can grow or when a later empty stored slot can be shifted forward.
- Cell context-menu push-down insertion places an empty stored slot immediately after the selected
  occupied slot and shifts following slots across boxes until it reaches later available room.
- Repeating either empty-slot insertion action after the same occupied slot can create multiple
  consecutive empty stored slots when later room still exists.
- Box menu move actions can move a box one position or directly to the top or bottom of the preset
  while preserving the box contents.
- Creating a classic preset appends a new key in `boxpresets/classic/GAME_SET.json`.
- Creating a modern preset appends the id to `boxpresets/modern/GAME_SET.json` and writes
  `boxpresets/modern/GAME_SET/PRESET_ID.json`.
- Deleting a modern preset removes it from the index and removes its per-preset file when present.

### Edge Cases

- Loaded and newly-created boxes should use the selected game set's `maxBoxSize`, filling free slots
  with editable `null` cells. Box creation should not exceed `maxBoxes` where available.
- Visual padding cells beyond the selected game set's box capacity are not stored cells and must not
  accept drops.
- Object-shaped cell values must preserve flags such as `gmax`, `shiny`, and `shinyLocked`, using
  classic `{ pid }` records for classic writes and modern `{ pokemon }` records for modern writes.
- Save actions must write only `boxpresets/classic` or `boxpresets/modern` paths for known game set
  ids, and modern save actions must update the selected preset file without rewriting the index.

## Implementation and remaining verification

Reusable editor behavior belongs in [`apps/editor/app/lib`](../apps/editor/app/lib), with filesystem
operations in sibling `*.server.ts` modules. Keep routes slim, preserve sibling files and index
entries, and validate writes against the dataset schemas. Pure logic and filesystem modules remain
separate. Tests belong beside the lib modules.

The Pokédex editor currently bounds National Dex values with `MAX_DEX_NUM=1386`; review the dataset
contract before changing it. The editor supports `data/` and loads images from the public CDN.
Editing `data-next/` and using offline images are outside its current scope.

The browser suite covers Pokédex persistence, preset creation, saving and deletion, and route
rendering. Further coverage is needed for pointer interactions, capacity errors, keyboard
navigation, narrow-screen layouts, availability writes and bulk-maintenance writes.

## Visual guidance

`apps/editor` is a local dataset maintenance tool. Favor dense, calm layouts that keep Pokemon and
game data visible and make edits easy to review and reverse.

- Use compact table, grid, drawer, and form layouts that keep Pokémon/game objects visible without
  turning maintenance screens into public marketing pages.
- Prioritize clear dirty state, save/cancel affordances, validation errors, and reviewable changes
  over decorative presentation.
- Box preset editing can use tactile drag/drop, sprite tiles, sticky actions, and warning states,
  but must make empty slots, unsupported forms, duplicates, and destructive actions visually
  explicit.
- Bulk maintenance screens should be quieter than player-facing screens: clear scope, previews,
  explicit commit actions, and minimal flourish.
- Prioritize operational clarity and document editor-specific visual decisions here.
